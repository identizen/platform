This page is for the person at a relying party who has to answer "what does Identizen store about our users, and where". It describes the hosted index at `index.identizen.com` as the code runs today. A self-hosted index stores the same records on your own infrastructure. The user-facing version is the [privacy policy](https://identizen.com/legal/privacy/); the deletion steps are on [Delete your identity and data](https://identizen.com/legal/delete/).

## What the index never has

No name, email address, phone number, or password. No private key: the seed, the master key, the per-site keys, and the device key live on the phone and are never sent. No plaintext secret: a site's client secret and webhook secret are stored as SHA-256 hashes. A person is known to the index by `idz`, a hash of their master public key, and to each site by a different `sub`, a hash of a key derived for that site's host. Sites cannot correlate a person across each other, and the index never sends `idz` to a site.

What `detail` holds in audit events, so there is no surprise: `login.success` carries `challenge_id`, `acr`, `sub`, and whether a binding was created; `login.denied` carries `challenge_id` and the error code; `verification.created` carries `verification_id` and `sub`; `session.created` carries `sid` and `acr`; `device.enrolled` carries the label the app sent; `pairing.*` carry the pairing id; `identity.handle_changed` carries the new handle; `site.created` carries `rp_id`. The `client_id` column on login, session, and verification events means the index knows which sites an identity signs in to. This routing metadata is inherent to a relay; an organisation that must keep it private runs its own index.

## Lifetimes that are fixed in code

| Item                                     | Lifetime                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------- |
| Challenge (login, step-up, verification) | 60 seconds; the `ttl` field on `POST /v1/verify` is accepted and ignored  |
| `ChallengeSession` state after resolving | Wiped 5 minutes later                                                     |
| Authorization code                       | Single use, inside the challenge session                                  |
| id_token, access token                   | 1 hour                                                                    |
| Back-channel logout token                | 2 minutes                                                                 |
| Verification webhook JWT                 | 10 minutes                                                                |
| OIDC session (`sid`)                     | 30 days, or until revoked                                                 |
| `Idz-Signature` request                  | Accepted within ±60 seconds; the same signature is rejected if seen again |

There is no scheduled job in the index. Rows in `sessions`, `verifications`, and `audit_events` are not deleted when they expire; they are removed when an identity's records are deleted on request.

## What a site receives

The id_token and `/userinfo` carry `sub` (per site), `sid`, `idz_device` (an opaque device id), `amr`, `acr`, and `idz_handle` when the site asks for the `handle` scope and the person has set one. `idz_org` appears for org identities; nothing assigns one today. The full list is on the [OIDC reference](/reference/oidc/#id_token-claims). A Verification API response adds the `reason` you sent back to you and the double-signed assertion. Nothing else about the person reaches a site, and a site cannot call `/me`: bearer access to account management is limited to the client ids in the index's `DASHBOARD_CLIENT_IDS`.

What you store under `sub` (profile, billing, KYC) is yours. The index never sees it. See [Users, sign-up, and linking identities](/users/).

## Where it runs

The hosted index is a Cloudflare Worker at `index.identizen.com`; Workers run at Cloudflare's edge, so a request is served near the caller. Durable Objects hold the transient state above. Postgres is on Neon, reached through Cloudflare Hyperdrive, in AWS `us-east-1` (United States). A person's persistent records therefore live in the United States regardless of where they are.

Hosting request logs (IP address, user agent, URL, time) are kept by the providers for a short period; the privacy policy says they expire within days. The index itself writes no request log; it logs unhandled errors and failed pushes.

## Subprocessors

| Provider                            | Role                                                                                                                                                                                                                                             |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Cloudflare, Inc.                    | Runs the Worker, Durable Objects, Hyperdrive, and the dashboard and websites                                                                                                                                                                     |
| Neon, Inc.                          | Hosts the Postgres database (AWS `us-east-1`)                                                                                                                                                                                                    |
| Expo (650 Industries, Inc.)         | Push relay. The app registers an Expo push token; the index posts `{ challenge_id }` to `exp.host`, which forwards to APNs or FCM. When the index holds an `EXPO_ACCESS_TOKEN` the request is authenticated with it                              |
| Apple Inc. (APNs), Google LLC (FCM) | Deliver the push to the phone. The index can also talk to APNs and FCM directly when a self-hosted operator configures the credentials; the payload is the same challenge id. The privacy policy names Apple and Expo for the hosted index today |

No analytics or advertising SDK is present in the phone app, the index, or the dashboard; their dependency lists contain none. The phone app's camera is used to read a QR code and no image leaves the phone.

## Data processing agreement

There is no published DPA yet. It is available on request for enterprise engagements, and the [enterprise roadmap](/enterprise/) lists it under compliance packaging with the SOC 2 report and EU/US data residency. Two things reduce what a DPA has to cover: the index holds no direct identifiers, and running your own index removes Identizen as a processor entirely, since no Identizen-operated service is in the path.

## Requests from your users

A person can revoke any device, session, or paired browser from the app or the dashboard, and remove the identity from a phone at any time. To have the hosted index delete or export everything it holds about an identity, they follow [the deletion page](https://identizen.com/legal/delete/): the request is confirmed by sending a sign-in challenge to that identity, so only its holder can trigger it, and it is completed within 30 days. That removes their `sub` bindings too; your own records for that `sub` are yours to handle under your own policy.
