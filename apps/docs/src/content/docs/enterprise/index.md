Identizen is open core. The protocol, the index (`@identizen/index`, every route it serves today), the database schema and migrations, the SDKs, the CLI and fake phone, the design system, the personal dashboard features and the mobile app are open under Apache-2.0 and stay that way. What is proprietary is the layer that runs the open index _for an organisation_: the multi-tenant control plane that provisions tenants, holds their sealed secrets and resolves hostnames, and the management surfaces built on top of it. Nothing proprietary changes what the open index promises, and nothing in it ever holds a private key.

## Two editions

| Edition             | What it is                                                                                                                                                                                                               | Status                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| **Identizen Cloud** | A dedicated index per organisation at `https://{tenant}.index.identizen.com`: its own issuer, its own signing keys, its own Postgres in a US or EU region, operated by Identizen. [Set it up](/enterprise/cloud-setup/). | Available today; provisioned by Identizen on request |
| **On-prem**         | The same code packaged as signed containers (compose bundle and Helm chart) with a signed licence, installed inside your own boundary. [Install](/enterprise/on-prem/).                                                  | Available from `ee-v0.6.0`; installed with Identizen |

If you need the index inside your boundary now, [self-hosting](/self-hosting/) the open index is supported today and needs no licence.

## Available today

- **A tenant index.** Every organisation on Identizen Cloud gets its own issuer, JWKS, challenge-signing key and database. A request for one tenant can never read another's: separate databases, host-pinned issuer, per-tenant Durable Object and cache namespaces, and a token minted by one tenant's issuer is rejected by every other. The tenant Worker's test suite includes isolation tests for exactly this.
- **Data residency.** Each tenant's Postgres lives in the US or the EU, chosen at provisioning and never moved ([details](/enterprise/cloud-setup/#data-residency)).
- **Closed registration.** Only holders of the tenant's registration token can register sites on its index.
- **The index as a library.** `@identizen/index` exposes `createApp(options)` with per-request bindings, policy hooks and extra routes, which is how the tenant Worker is built ([embedding](/embedding/)).
- **MFA and step-up.** `acr_values=idz:mfa` with `login_hint=<sub>`, the Verification API, and an honest `amr` that refuses to call an unverified approval a second factor ([recipe](/enterprise/mfa-and-step-up/)).
- **Instant revocation with back-channel logout.** Revoking a device (`POST /me/devices/:id/revoke`) or a session ends every live OIDC session for it and POSTs a logout token to each site's `backchannel_logout_uri` immediately, retried for a few seconds on failure.
- **Audit events.** Every login, denial, enrollment, pairing, session, verification and revocation writes an `audit_events` row (`GET /me/audit` for the user's own view).
- **Domain verification.** A live site must prove its `rp_id` by DNS TXT or the well-known file before it can start logins, on a tenant index exactly as on the public one.
- **Admin portal.** `https://{tenant}.portal.identizen.com`: the organisation's profile (display name, logo), verified domains (DNS TXT or well-known file), users with the roles `owner`, `admin`, `helpdesk`, `auditor` and `member`, suspend, reinstate and deprovision, devices, approvals, policy, sites, sessions, MDM, and two audit logs (org events with filters; admin actions with before and after). Identizen invites the first owner at provisioning ([details](/enterprise/portal/)).
- **Org app.** `https://{tenant}.app.identizen.com`: the dashboard (devices, paired browsers, sessions, activity, settings) deployed per tenant, with the organisation's name and logo, a "managed by" line, and a notice while a membership is suspended ([details](/enterprise/org-app/)).
- **Invitations, by email.** An administrator invites by email and role and gets a link, shown once, valid 7 days; the person enrols a phone on the tenant index, opens the link, signs in and accepts. The tenant index also emails the link (through Resend, configured per index by Identizen) and reports `delivery.email` as `sent`, `failed` or `not_configured`; the link is always shown as well, so an administrator can pass it on by hand. Enrollments an administrator issues from a user's page are emailed the same way; self-service and MDM enrollments are not ([details](/enterprise/portal/#inviting)).
- **Phone enrollment.** A one-time enrollment token, issued by an administrator from a user's page, by a member for their own phone in the org app, or by an MDM, carried as an `identizen://enroll?index=…&token=…` link or QR code. The phone shows the organisation, registers on the tenant index if it is not there yet, and claims with its device signature; the enrollment is then approved automatically by policy or waits in the portal's **Approvals** queue. The phone app's side of this ships in the next app build ([details](/enterprise/enrollment/)).
- **Fleet console.** **Devices** in the portal lists every phone and browser key of every member, with search and filters, last seen, managed or not and attestation status. Disable ends the phone's sessions and blocks its logins until it is enabled again; revoke is final ([details](/enterprise/enrollment/#the-fleet-page)).
- **Enrollment policy.** `require_attestation`, `auto_approve`, `auto_approve_mdm` and `enrollment_ttl_hours`, applied at claim time from a snapshot taken when the token was issued ([reference](/enterprise/enrollment/#policy-reference)).
- **MDM integration.** MDM tokens created in the portal, `POST /enroll/mdm/issue` to obtain a per-user enrollment, and the managed app configuration profile (`index_url`, `enrollment_endpoint`, `enrollment_token`) with an Intune and a Jamf recipe. The phone app does not read managed app configuration yet; the deep link the endpoint returns is what reaches the phone today ([details](/enterprise/mdm/)).
- **Device attestation, server side.** The tenant index verifies Apple App Attest offline and Google Play Integrity through Google, and records `none`, `unverified`, `verified` or `failed` per enrollment and device. No phone build sends an attestation yet, so today every claim is `none` and `require_attestation` refuses every enrolment ([details](/enterprise/mdm/#attestation)).
- **Membership enforced at login.** An identity linked to a suspended or deprovisioned member is refused at phone approval and at code exchange (`member_suspended`, `member_deprovisioned`), audited as `login.denied`. Suspension revokes every session; deprovisioning revokes every device and session; both send back-channel logout.
- **Login policy.** Organisation-wide rules for members, applied at phone approval: `require_managed_device` (only enrolled phones; with a preview of who would be locked out), `allowed_amr` (for instance biometrics only), `login_windows` (weekdays and local hours in a named timezone, wrapping midnight allowed), and `session_max_age_hours`, applied at code exchange and only ever shortening a session. Refusals are `managed_device_required`, `amr_not_allowed` and `outside_login_window`, audited as `login.denied`. Active members get `idz_role` in the id_token and `/userinfo` ([reference](/enterprise/policy/)).
- **Workforce-only sites.** **Sites** in the portal lists every site on the tenant with its verification state and lets an administrator rename it or mark it workforce-only, which refuses anyone who is not an active member (`workforce_only`). `workforce_only_default` in the policy is stored but not yet applied to new sites ([details](/enterprise/policy/#sites-and-workforce-only)).
- **Sessions.** **Sessions** in the portal lists live member sessions across sites; helpdesk can sign one member out, and an owner or admin can sign everyone out after typing the organisation's slug, with back-channel logout to every site either way ([details](/enterprise/portal/#sessions)).
- **OIDC apps.** **SSO** in the portal registers the organisation's own applications as OIDC clients on the tenant index (public or confidential, secret shown once), with **release profile** so active members' `email`, `name` and `idz_role` reach the app, workforce-only per app, and disable, which refuses every login with `app_disabled` ([details](/enterprise/sso/)).
- **SAML identity provider.** The tenant index serves SAML 2.0 metadata and an SSO endpoint; SAML apps are registered with their entity id, ACS URL, NameID format and attribute map, and sign in through the normal phone approval. Signed assertions, Redirect and POST bindings, IdP-initiated test logins, members only. No single logout yet ([details](/enterprise/sso/#the-saml-identity-provider)).
- **SCIM 2.0 provisioning.** `/scim/v2` with tokens created in the portal: Okta and Entra create members (invited by email), update names, suspend with `active: false` (sessions revoked) and deprovision on delete (devices and sessions revoked). Owners and admins are protected. Every call is logged ([details](/enterprise/scim/)).
- **Audit export and SIEM webhooks.** **Compliance** in the portal exports the audit log (CSV or JSON, date range) and the organisation's data as downloadable files kept 7 days, and streams every audit event to webhooks signed with the tenant's Ed25519 index key, with retries over 24 hours, a delivery log and a test event ([details](/enterprise/compliance/)).
- **Retention, status and quotas.** Retention periods for audit events, admin actions, the SCIM log and webhook deliveries, applied daily by the index's scheduled jobs; a status page with the plan's quotas (members, devices, SSO apps, SCIM tokens, webhooks), job runs and health; a public `GET /status` per tenant ([details](/enterprise/compliance/#status-and-quotas)).
- **Key rotation with overlap.** OIDC signing keys rotate by prepending a new key and pruning the old one after the overlap; the index key and the SAML key rotate on request; the sealing key that protects every tenant's secrets rotates with a re-seal, all run by Identizen ([cloud setup](/enterprise/cloud-setup/)).
- **On-prem edition.** Signed images with SBOMs, a compose bundle for pilots, a Helm chart with a migration Job for production, a licence with 14-day grace and seat counts, and a Postgres-backed challenge store for several index replicas ([install](/enterprise/on-prem/)).
- **Dashboard as a package.** `@identizen/dashboard` (sign-in, devices, paired browsers, sessions, activity) is published so an organisation can also compose it into its own app pointed at its tenant issuer; the org app above is this package deployed by Identizen.
- **Two identity kinds and `idz_org`.** Identities carry `kind: 'personal' | 'org'` and an optional `org_id`; the id_token and `/userinfo` carry `idz_org` for identities that have one. Org membership lives in the org's member list and does not yet set the identity's `org_id`, so `idz_org` is still absent; `idz_role` is what a site sees for a member today.

## On the roadmap

No dates. Nothing below is built; treat all of it as absent when you integrate.

| Capability                     | Notes                                                                                                                                                                         |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Attestation on the phone       | The native App Attest and Play Integrity module in the Identizen app, so that claims carry an attestation and `require_attestation` becomes usable. The server side is built. |
| Self-enrolment by domain       | Joining with a verified email domain (the `auto_join` flag is stored today, not acted on).                                                                                    |
| Policy, the rest               | Geo rules, scheduled re-checks of enrolled devices, `workforce_only_default` actually applied to newly registered sites, ending live sessions when a login window closes.     |
| `idz_org`                      | Setting `org_id` on identities at membership so `idz_org` is carried; today a site sees `idz_role` only.                                                                      |
| SSO, the rest                  | SAML single logout, encrypted assertions, SP metadata import, and Identizen as an external IdP federated into Okta or Entra (today it signs in to apps directly).             |
| SCIM groups                    | Group push and group-based role assignment; today SCIM manages users only and every provisioned member has the `member` role.                                                 |
| Operations, the rest           | Scheduled domain re-checks, custom domains (`login.example.com`), audit export streaming for very large logs (exports are assembled in memory today), SAML single logout.     |
| Compliance packaging           | SOC 2 report, DPA, pen-test summary.                                                                                                                                          |
| Self-serve sign-up and billing | Today provisioning is done by Identizen; there is no sign-up form.                                                                                                            |

## What the org never gets

The org never holds a private key and cannot log in as a user. Revocation is the org's power; impersonation is not. The index stores public keys, push tokens, revocation state, and audit events, and nothing that could be used to sign an assertion. That holds for a tenant index, for a self-hosted one, for the portal that exists today, and for every roadmap item above: hooks and policies can refuse a login; they cannot approve one.
