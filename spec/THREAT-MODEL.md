# Identizen — Threat Model (v1)

**Status:** current as of protocol v1 and the shipped index, SDKs, CLI, fake phone, and phone apps. Not yet externally reviewed; an independent review is planned before 1.0. Report problems through [SECURITY.md](../SECURITY.md).
**Scope:** the index (Cloudflare Worker + Durable Objects + Postgres), the hosted login page, the SDKs, the CLI, the fake phone, the iOS and Android apps, and the protocol as implemented in `packages/protocol`. The passkey provider and desktop companion described in the protocol are out of scope until they exist.

## 1. Assets and trust boundaries

| Asset                                                                                                   | Where                                                                                                                    | Who may hold it                                            |
| ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| Seed / master key / per-site keys                                                                       | Phone only: platform keychain or keystore, biometric-gated when enabled (Secure Enclave / StrongBox wrapping is planned) | The user. Never the index, never a site.                   |
| Device key                                                                                              | Phone only, same storage                                                                                                 | The install.                                               |
| Index signing key (`INDEX_SIGNING_KEY`)                                                                 | Worker secret                                                                                                            | The index operator. Signs challenges and pairings.         |
| OP signing keys (`OIDC_SIGNING_KEYS`)                                                                   | Worker secret                                                                                                            | The index operator. Signs id/access/logout/webhook tokens. |
| Site client secret                                                                                      | The site's server; only its SHA-256 in `sites.client_secret_hash`                                                        | The site.                                                  |
| Browser pairing key (P-256, non-extractable)                                                            | Browser IndexedDB, per origin                                                                                            | That browser profile.                                      |
| Public keys, push tokens, BLE HMAC keys, revocation state, audit, paired-browser user agent and last IP | Postgres                                                                                                                 | The index. **Nothing here lets anyone log in.**            |
| In-flight challenge, OIDC params, one authorization code                                                | `ChallengeSession` DO, ≤ 5 min                                                                                           | The index.                                                 |

Trust boundaries: phone ↔ index (TLS, Idz-Signature), browser ↔ index (TLS, WebSocket), site ↔ index (TLS, OIDC / client secret), index ↔ push provider (APNs/FCM via the Expo push relay; the payload is only a challenge id).

## 2. Attackers considered

- **Phisher:** controls a lookalike site and can start logins.
- **Network attacker:** can observe / inject on the user's network but not break TLS.
- **Push bomber:** can trigger many challenges toward a device.
- **Index breach:** reads the entire database and Worker secrets.
- **Malicious site:** a legitimately registered relying party acting badly.
- **Lost / stolen phone** (locked), and **rogue second device** (attacker restores a leaked recovery phrase).
- **Malicious paired browser** (malware on a paired laptop).
- **Prompt-injected agent:** software acting for the user asks for one thing and attempts another.

## 3. Guarantees and how they hold

| Threat                                                       | Mitigation in the code                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Phishing on a lookalike domain                               | `rp_id` is inside the signed assertion; the index verifies `rp_id == challenge.rp_id`, the site key is derived per `rp_id`, and the OIDC code is bound to the registered `redirect_uri` + PKCE. A signature for `evil.example` never verifies for `app.example.com` (`verifyAssertion` → `rp_id_mismatch`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Index made to call arbitrary URLs (SSRF, slow endpoints)     | Every destination somebody else supplies (a device's web push URL, a site's webhook and back-channel logout endpoint) passes an egress policy when it is registered and again before every request: https only, no credentials in the URL, no loopback, private, link-local or CGNAT address and no local hostname; each attempt has a five-second deadline that covers the response body as well as the headers, the body is read at most to a 64 KiB cap, and redirects are not followed. Hostnames are canonicalized first (lower-case, trailing root dots removed), so `localhost.` is `localhost`. `OUTBOUND_ALLOW_LOCAL=true` relaxes the address and scheme rules for local development only. The index cannot resolve DNS before connecting, so a public name that resolves to a private address is for the self-hoster's network policy. |
| Replay of an assertion or a request                          | Assertions carry the challenge nonce, are accepted once (DO state `pending` → terminal), and expire at 60 s. `Idz-Signature` includes method, path, body hash, and timestamp; the `RequestGuard` DO rejects any `(timestamp, sig)` seen before within ±60 s. The replay window, the per-device quotas and the inbox live in Durable Object storage, not memory, so an eviction, deploy or restart neither reopens a window nor drops a queued challenge.                                                                                                                                                                                                                                                                                                                                                                                          |
| Push bombing / fatigue                                       | Every approval shows the 2-digit match code and the site name; every push to a device, whoever asked for it (discovery, a step-up, the Verification API), counts against `RequestGuard.allowPush`, at most ten per device per minute (`429 push_rate_limited`); challenge issuance is limited per site client and per source IP.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Index database breach                                        | Stores only public keys, push tokens, BLE HMAC keys, revocation state, audit, and paired-browser metadata. No private keys, no secrets in plaintext (client and webhook secrets are hashed). A breach yields nothing that produces a valid `site_sig` or `device_sig`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Index secret compromise (Worker secrets)                     | Attacker could sign challenges and pairings (index key) and mint tokens (OP keys). Mitigations: secrets live only in Cloudflare; rotation is supported for OP keys (two active keys) and for the index key by cross-certification (PROTOCOL.md §3.1: the retiring key signs a statement naming its successor, published at `/.well-known/identizen`, and phones re-pin along the signed chain). A compromised index key cannot be recovered by rotation alone, since its holder can sign a rotation too; those phones re-register.                                                                                                                                                                                                                                                                                                                |
| Malicious site correlating users                             | `sub` is a hash of a per-site key and `idz_device` is derived per site the same way (PROTOCOL.md §5); `idz` and the index-side `device_id` are never released through OIDC. The handle is released only to sites that request the `handle` scope, and only if the user set one. **Known limit:** a Verification API result carries the phone's signed assertion, whose `device_id` is the index-side one, so two sites that both use the Verification API and pool raw assertions could match a phone that way.                                                                                                                                                                                                                                                                                                                                   |
| Site enumerating other users' state                          | `/me/*` bearer access is restricted to clients in `DASHBOARD_CLIENT_IDS`; ordinary sites only ever see their own `sub`. Verification API records are readable only by the owning client.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Stolen locked phone                                          | Keys are behind the device biometric or passcode. The user revokes from another device or the dashboard; revocation invalidates `device_sig`, all pairings, and fires back-channel logout.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Replayed enrollment proof                                    | The identity proof is bound to the index URL and a two-minute nonce (PROTOCOL.md §8.1), and a device key is enrolled at most once: a revoked key cannot be enrolled again with any proof, old or new (`403 device_revoked`), and an active key registering again gets its existing row rather than a second one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Rogue second device from a leaked passphrase                 | Same identity, new device: audit shows `device.enrolled`; the legitimate user can revoke it. Custody of the 24 words is the user's. Shamir or second-device recovery is a future item.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Malicious paired browser                                     | A pairing only skips discovery. Approval still requires the phone and the match code. Pairings are listed and revocable, and die with the device.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| BLE tracking                                                 | Rotating identifiers (HMAC over a 15-minute window) resolvable only by the index.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Token theft (access token)                                   | Access tokens are 1 h JWTs bound to a session; `/userinfo` and `/me` check session liveness, so revocation takes effect immediately.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Webhook forgery                                              | Verification results are signed JWTs (`typ: idz-webhook+jwt`, ES256, audience = client id) plus an informational HMAC header.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Substituted action (agent or malware asks for A, executes B) | The reason text is composed by the site's server, shown on the phone, and its hash is inside the signed assertion. An approval for one text does not verify for another.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Challenge takeover (attacker learns a challenge id)          | A challenge issued for a person (step-up `login_hint`, Verification API `sub`) records that identity and `sub` at creation and never changes them: discovery cannot re-route it to another identity (`403 wrong_identity`), only that identity's devices may approve or deny it, and the assertion `sub` must match (`403 wrong_subject`). An untargeted challenge is routed by discovery once (`409 challenge_targeted`). The session moves to approved before any Verification API record or webhook is written.                                                                                                                                                                                                                                                                                                                                |
| Code issued to an unregistered redirect                      | `/authorize` and the JSON `/challenge` share one validator: exact match against the registered redirect URIs, PKCE S256, known scopes, `prompt` semantics. `/token` checks the redirect against the registration again at redemption. A code is bound to its client and redirect before anything about it is disclosed: another client presenting a spent code gets a plain `invalid_grant` and triggers no reuse revocation (F05).                                                                                                                                                                                                                                                                                                                                                                                                               |
| Burning or partially redeeming a code                        | Redemption is one operation inside the session: client, registered and matching redirect, PKCE verifier, and a five-minute expiry are all checked before the code is marked used, so a wrong verifier cannot consume a legitimate login. A second presentation of a used code revokes the session the first exchange created.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Site registration abuse (registering a name you do not own)  | Registration is open, but a live site cannot start a login until it proves control of its `rp_id` (PROTOCOL.md §8.2): a DNS TXT record at the host or a parent zone, or the well-known file over HTTPS, each carrying the token issued at registration. Verification is re-checked after thirty days; unverified registrations expire after forty-eight hours; several registrations per host are allowed, each proving the domain itself. The record can pin the index (`index=`). Client ids are unguessable ULIDs. `SITE_REGISTRATION_TOKEN` remains for indexes that want registration closed as well. The proof is decided by the host, never by the `idz_test_`/`idz_live_` label the registrant picks.                                                                                                                                     |
| Revocation racing session issuance                           | A session is inserted inside a transaction that share-locks its device row and checks `status = active`; `setDeviceStatus` locks the same row for update, so a revocation either refuses the insert or waits for it and then ends the new session too. Bearer use (`/userinfo`, `/me/*`) re-checks the device's status, so a session whose device is gone is dead even if its row were left live (F02).                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Denial or expiry racing an approval's writes                 | The assertion route claims the session before writing anything durable (PROTOCOL.md §4.1 step 7): a denial that got there first wins and no binding, pairing or success audit exists for it; a decline that arrives during the writes is refused (`409 approval_in_progress`) and expiry waits a short grace; if the writes fail the claim is released and a pairing already written is revoked (F03).                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Concurrent enrollment of one device key                      | `devices.device_pubkey` is unique in the database (migration 0003), and enrollment is an idempotent insert: the second of two racing registrations receives the row the first created and answers as a repeated registration would, so a revocation always covers the key. Pre-existing duplicates were tombstoned by the migration (F04).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Browser-side hardening and cross-origin calls                | Every index response carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` and, over https, HSTS. The hosted login page has a per-response nonce CSP (`default-src 'none'`, only its own script and style, `connect-src` the index and its WebSocket, `frame-ancestors 'none'`); the root page a static one. CORS is per route: login, discovery and token endpoints answer any origin, since an OIDC public client is whatever site the person is on; `/me/*` answers only `APP_URL`'s origin and `CORS_ALLOWED_ORIGINS`. The dashboard, docs and marketing sites ship a CSP (hash-based for the Astro sites, checked at build time) and the same header baseline (F08).                                                                                                                            |
| Request cost from an anonymous caller                        | Signed request bodies are read with a 64 KiB cap and any declared body over 1 MiB is refused before a route runs (`413 payload_too_large`); `/discover/ble` scans at most `BLE_LOOKUP_LIMIT` recently seen advertisers through a partial index; `X-Forwarded-For` is believed only behind a declared proxy (`TRUST_PROXY_HEADERS=true`), so a caller cannot choose their own rate-limit bucket (F09).                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Generated integrations losing revocations across instances   | The scaffolded Express and Next.js integrations refuse to run with `NODE_ENV=production` on their process-local revocation store until it is replaced by a shared one (`IDENTIZEN_ALLOW_MEMORY_REVOCATIONS=true` is the explicit single-instance opt-out), so a multi-instance deployment cannot silently forget a back-channel logout (F10).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| A site missing a webhook or a logout while it is down        | Every Verification API result and back-channel logout is a `deliveries` row before it is a request: tried once in the request, then retried by the scheduled sweep with backoff over about two days (nine attempts), each with a token minted at send time; a refusal (4xx other than 429) or an exhausted schedule ends it with a `delivery.failed` audit event the site can see. Sweepers claim rows under a lease (`FOR UPDATE SKIP LOCKED`), so replicas and an overlapping cron never send one twice.                                                                                                                                                                                                                                                                                                                                        |
| Seed compromise, and data that outlives its purpose          | `DELETE /me` removes an identity and everything about it in one transaction, sends a logout to every live session's site first, and leaves a tombstone: with `reason: compromised` the master key can never enroll again (the attacker holds the seed too), so the person starts over with a new seed and re-links at each site. The scheduled sweep purges ended sessions, resolved verifications and settled deliveries after thirty days, unverified registrations after two, and audit events after `AUDIT_RETENTION_DAYS` (a year by default).                                                                                                                                                                                                                                                                                               |

## 4. Residual risks (accepted for now)

- **Index operator trust.** The operator can issue challenges for any site to any device (the user still has to approve on the phone with the code displayed) and can mint tokens for any `sub` (a site cannot detect a forged approval unless it also checks the double-signed assertion via the Verification API). Self-hosting removes this trust for regulated deployments.
- **Key storage on the phone.** Keys are protected by the platform keychain or keystore and the device biometric, not yet by a hardware-isolated key. `amr` says exactly what happened at the gate (PROTOCOL.md §4): a biometric only when a biometrics-only prompt succeeded, `pin` for the passcode, `user` when the platform cannot name the biometric, `swk` when the prompt was skipped, and never `hwk` until enclave-backed keys ship. The index refuses a step-up whose assertion verified nobody.
- **Device time skew.** ±5 s (assertion) / ±60 s (request) windows; badly skewed phones fail closed.
- **APNs/FCM as a dependency.** Transport only; payload is `{ challenge_id }`. Every challenge is also queued in the device's inbox, so delivery does not depend on the push provider.
- **Code in the front channel.** Standard OIDC; PKCE + single-use + client binding limit the blast radius.
- **Hosted login page and pairing on the index origin.** The pairing key in IndexedDB is per origin; XSS on the index origin would be catastrophic. The page is static HTML with no third-party scripts and `X-Frame-Options: DENY`.
- **Routing metadata.** The index necessarily learns which sites an identity signs in to. Sites cannot correlate a person across each other by `sub` (but see the open device-id item above); an organization that must keep this metadata private runs its own index.
